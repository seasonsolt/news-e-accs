# 计划：信源扩容与模型全部改用 Codex 订阅

> 2026-10-12 起草。记录这次改动的原因、已经做了什么、怎么控制额度、要盯什么、怎么回退。
> 只属于我们自己的生产站（e-acc.ai），不是模板的通用说明；通用用法见 `docs/deploy.md` 的“文字步骤用 Codex 模型”。

## 1. 背景

2026-10-12 早上首页最新一天只有 10/11 的 2 条，当天日报也只有这 2 条。排查结论（只读，没有改动）：

- 日报、模型、抓取三个环节都正常：08:00 日报照常生成，中文版也翻译好了；模型处理没有失败；38 个信源里 37 个状态正常。
- 原因是没有新东西可选：采集量从 10-08 的 94 篇一路降到 10-12 早上的 7 篇。雷锋网的 feed 从 10-10 19:40 到 10-12 08:41 一篇没更新，量子位凌晨一直 304，英文源周末也基本停更。
- 根子在信源太单薄，一到周末就断粮。

使用者的决定：**不加新的 RSS，扩大 X 的采集面**；**模型从 DeepSeek API 改用已经付费的 Codex 订阅**（订阅是沉没成本）。

## 2. 合规边界

用 OpenAI 认可的方式用订阅，不把订阅变成 API：

- 认可的：官方客户端（Codex App、CLI、SDK）或支持 Sign in with ChatGPT 的客户端，本人账号、本人额度。官方认证文档也写明 ChatGPT 登录态可以给可信机器上的脚本和定时任务用。
- 不认可、会被风控标记的：把订阅转成 API 流量再给别的程序用，例如 sub2api、CLIProxyAPI 这类网关。Codex 负责人 Tibo（@thsottiaux）2026-08-21 发帖点过名。
- 所以我们的做法是：worker 直接调用服务器上用 ChatGPT 登录的官方 `codex exec`（`CODEX_HOME=/srv/eacc/codex`），不搭任何 HTTP 代理。

## 4. 额度和用量怎么控制

订阅是固定费用，要控的是**额度**，免得把账号的 5 小时窗口用光、连人写代码也被挤掉。

1. **预算熔断**：`codex-text` 每分钟 20、每小时 300、每天 3000 次。超出时不发请求，这一步顺延到下一轮。在后台“预算”页填 0 就全部停下。配图另有一行 `codex`，两者互不挤占。
2. **按步骤挑模型**：批量的步骤用 luna，写作的步骤用 sol，推理强度都是 low。
3. **回执复用**：同一个请求重试时复用已经收到的答案，不会重复消耗额度。
4. **随时回退**：后台“模型与评测”页把任意一步切回 `default`（DeepSeek），1 分钟内生效，不用发布。
5. **额度用完时**：Codex 报错，回执记为失败，下一轮再试。**不会自动切回 DeepSeek**（项目约定没有证据就不加兜底），需要人工切换。

量级估计：切换前 7 天共 4,260 次模型调用（每天约 610 次）。X 扩容后预计每天 1,000 到 1,500 次，在 3000 次的日上限以内。每次调用约 8,600 输入 token（大部分命中缓存）。OpenAI 不公开各套餐的额度换算，**具体会占账号多少额度只能实测**。

## 5. 已知风险

1. **入选门槛没有重新校准。** 门槛 T1 60、T1_5 65、T2 76 是按原来的模型定的，换 GPT 打分后分数分布可能偏移。按 `AGENTS.md` 的约定，要用使用者标注的样本重新校准（`docs/selection.md`），不能凭感觉改数字。
2. **处理变慢。** DeepSeek 每次约 1 秒，Codex 约 3 秒；再加上每分钟 20 次的预算，集中进来一批文章时（比如 09:29 那一分钟就有 255 次调用）要排几分钟到十几分钟。
3. **归组复核失去独立性。** 复核原本建议换一家模型，现在和归组是同一个模型，事件误合并可能变多。
4. **翻译格式不稳定。** 切换后第一次全文翻译就被拒收（“translation prose must use zh”）。已有的拒收机制会重试，同一篇失败 3 次后保持原文。
5. **告警发不出去。** `FEISHU_INTERNAL_ENABLED` 关着，Codex 额度用完、采集停了，都没人知道。
