# Story depth and editorial review

`/admin/review` is the shared editorial review entry point. It lists all open story-depth requests (queued, pending or failed), source evidence, editable drafts, and field-by-field differences against the published version. The story chooser lists 30 stories per page and accepts a title or public ID search. The editor chooses the initial 30 stories; no stories are selected automatically.

The admin's **Deepen / Re-draft** command enqueues `story-depth.draft`. Only the worker calls `chatJson`, with receipts and the existing provider budget. The `storyDepth` model step defaults to `default` in `site/models.ts`; `STORY_DEPTH_MODEL` or the existing admin model selector can override it. `MODEL_CALLS_ENABLED` must be explicitly enabled in the API and worker to request and generate drafts. It remains off by default. The prompt is `industry/prompts/story-depth.md`.

Drafts use at most the latest 40 current public evidence reports, including extracted fact conditions and source quotes. Every key number must appear verbatim in its cited quote; quotes must occur in that report's supplied evidence. Citations cannot name another story's reports, and curve links must name an installed index page. This checks provenance, not the truth of a source's claim or the soundness of the interpretation: the reviewer must check those, edit the text, and record a review note before publishing.

Saving edits does not publish. Publishing atomically supersedes the earlier published revision; rejection never removes the approved version. Concurrent or stale review commands are refused. A queued request can also be rejected; a late worker response cannot revive it. Failed requests show in the queue and can be rejected before requesting another. The worker uses no automatic retries; paid provider responses remain in the existing receipt system.

Public story detail reads approved depth through `backend/publication.ts`, via the engine's generic `storyPage` module hook. Re-drafting does not affect the published version. If a source report is withdrawn, regrouped or corrected, or the story is merged, the stored depth is hidden until its evidence is current again or a new version is approved. Newly arriving reports alone do not remove approved depth. Readers never trigger generation. The block is English in both editions and explicitly has `lang="en"`; it is not submitted to content translation. Existing story indexing is unchanged (story pages are already indexable).

The module owns `editorial_reviews`: typed by `kind` and `subject_id`, with separate draft/review/publication states, optimistic versions, reviewer identity, notes, source snapshots and receipt IDs. A later essay kind can share this table, queue location, navigation badge and review conventions; only story depth is implemented now. Three module migrations create the table and concurrent unique indexes; they neither alter nor delete existing content. Module registration is in the three `site/modules/` lists, `site/package.json` and the Dockerfile.

Tests in `tests/story-depth.test.ts` use the existing isolated test database and a local HTTP model fake. They cover the queue command, worker, receipts, approval and rejection, re-draft diff, stale edits/evidence, cancellation, the model valve, private admin routes, anonymous publication, and English/Chinese story rendering through the production web build.
